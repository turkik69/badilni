# بادلني — تجهيز الإصدار للمتجرين

هذه الملفات تجهز المصدر. لا تعتبر النسخة موقعة أو مجربة على الأجهزة أو منشورة حتى تستكمل البنود المرتبطة بحسابي المطور.

## اللغة

يمكن للمستخدم التبديل بين العربية والإنجليزية من شاشة الدخول أو الشريط العلوي. يحفظ الاختيار محلياً. تُعرض نصوص الواجهة وتواريخها بالإنجليزية عند اختيارها؛ بيانات الإعلانات والمحادثات التي يكتبها المستخدمون تبقى بلغتها الأصلية. افحص الشاشتين يدوياً على أجهزة فعلية قبل الإرسال.

## Android — مفتاح رفع خاص

1. بعد إنشاء حساب Play Console، احفظ مفتاح الرفع خارج Git وفي مكان خاص له نسخة احتياطية منفصلة. أنشئه تفاعلياً مرة واحدة من جهاز موثوق:

   `scripts/create-android-upload-key.sh /secure/backup/badilni-upload.jks`

2. احفظ كلمة مرور المفتاح في مدير كلمات مرور، واحفظ نسخة احتياطية من ملف `.jks` في مكان مختلف. لا ترسل أياً منهما في المحادثة أو إلى المستودع.
3. عرّف المتغيرات `BADILNI_UPLOAD_KEYSTORE` بمسار الملف، و`BADILNI_UPLOAD_ALIAS=badilni-upload`، و`BADILNI_UPLOAD_STORE_PASSWORD` و`BADILNI_UPLOAD_KEY_PASSWORD` في بيئة بناء آمنة. يرفض Gradle بناء `bundleRelease` أو `assembleRelease` إذا غاب أي منها.
4. نفذ `npm run native:sync` ثم `cd android && ./gradlew bundleRelease`. الناتج AAB في `android/app/build/outputs/bundle/release/`. ارفع AAB إلى مسار الاختبار الداخلي وفعّل Play App Signing. احتفظ بنفس مفتاح الرفع للإصدارات التالية.

## iPhone — التوقيع والإشعارات

1. بعد تفعيل Apple Developer، سجّل دخول فريقك في Xcode وحدد Team لهدف App ذي المعرف `com.byyassmin.badilni`. التوقيع تلقائي، ولا يمكن إنشاء شهادة توزيع أو ملف provisioning حقيقيين قبل ربط الفريق. تأكد من ظهور Push Notifications ضمن Signing & Capabilities ومن تطابق entitlement مع التوقيع في الأرشيف.
2. أنشئ مفتاح APNs Auth Key من Apple Developer، واحفظ ملف `.p8` مع Key ID وTeam ID في مكان آمن؛ لا تضعها في Git. ارفع المفتاح في Firebase Console > Project settings > Cloud Messaging > Apple app `com.byyassmin.badilni`. راجع سجلات تسجيل الرمز FCM وتجربة إشعار على iPhone حقيقي، في الخلفية والمقدمة.
3. على Mac مع Xcode، نفذ `npm run native:sync` وافتح `ios/App/App.xcodeproj`، ثم Archive ووزّع إلى TestFlight. أضف حسابات اختبار حقيقية وراجع البناء قبل إرسال مراجعة المتجر.

## اختبار قبول قبل النشر

- iPhone فعلي وAndroid فعلي، العربية والإنجليزية: تسجيل حساب 13+، رسالة التوثيق، تسجيل الخروج والعودة، استعادة كلمة المرور، واتجاه الواجهة.
- بحسابين مختلفين: نشر غرض بصورة، ظهوره للحساب الآخر، البحث والتصنيف، تقديم عرض مباشر، المحادثة، القبول أو الرفض، وتأكيد الاستلام من الطرفين. جرّب الإبلاغ والحظر وتعديل الإعلان وحذفه.
- اختبر الأذونات والإشعارات في المقدمة والخلفية بعد رفع APNs؛ وعلى Android 13+ اطلب إذن إشعارات النظام. افحص التطبيق في وضع اتصال ضعيف وإعادة الفتح بعد تحديث النسخة.
- راجع صفحة الخصوصية والحذف، تصنيف العمر، لقطات المتجر، سياسة المحتوى الذي ينشئه المستخدمون، معلومات الدعم، وسياسات خصوصية المنصتين داخل حسابي المتجر.
- نفذ `npm run release:check` و`npm run native:release-check` ثم ابنِ النسخ الموقعة. نجاح اختبارات المصدر لا يحل محل اختبارات الأجهزة أو موافقة المتجر.

## عناصر مؤجلة حتى اكتمال الحسابات

| العنصر | ما يلزم من المالك |
|---|---|
| شهادة Apple وملف التوزيع | عضوية Apple Developer وTeam مرتبط بـ Xcode |
| APNs Auth Key | مفتاح `.p8` من فريق Apple وKey ID وTeam ID، ثم رفعه إلى Firebase |
| Android upload key | إنشاء تفاعلي على جهاز موثوق وحفظ الملف وكلمة المرور بشكل منفصل |
| المتجران | بيانات الحسابات والنماذج الرسمية ومراجعة TestFlight / Play internal testing |

لا تنشئ حسابات مستخدمين وهميين لإظهار نشاط في السوق. افحص الأداء باختبار تحميل اصطناعي معزول، واجمع مستخدمين حقيقيين عبر الإصدار التجريبي.
